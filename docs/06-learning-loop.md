# 学习闭环：从"看见"到"学会"

前面所有工具都只解决"看见"。这份文档解决"学会"。

## 一个反模式

多数人的逆向过程是：拆包 → 惊叹 → 截几张图 → 关掉 → 一周后什么都不记得。

原因是没有输出约束。**解药是每次逆向都必须产出两样东西：一份结构化报告，一个最小复现工程。**

## 报告模板

`urecon report` 自动填充前面几节（客观事实），最后两节必须手写。

```markdown
# <游戏名> v<版本> 逆向学习报告

## 1. 基础指纹        ← 自动
Unity 版本 / 脚本后端 / 热更方案 / 平台 / 包体构成

## 2. 技术栈清单      ← 自动 + 人工确认
第三方库、中间件、渲染管线、UI 框架、网络方案

## 3. 资源管线        ← 自动
分包策略 / 压缩 / 贴图格式 / 依赖 / 首包与热更边界

## 4. 代码架构        ← 人工
分层、模块划分、核心 Manager、数据流向。画一张图。

## 5. 三个"我没想到"  ← 人工，必填
让你意外的三个设计决策。为什么意外？他们为什么这么做？
代价是什么？——这一节是整份报告价值密度最高的部分。

## 6. 可迁移清单      ← 人工，必填
列出能用到自己项目里的东西，每条标注：
  - 是什么
  - 适用前提（他们的规模/品类下成立，我的呢？）
  - 复现难度
```

第 5 节是关键。"他们用了 Addressables"没有价值，"他们把 Addressables 的 catalog 拆成了按功能模块的多个远程 catalog，这样单模块更新不用重下全量 catalog"才有价值。

## 最小复现

从第 6 节里挑一条，在空工程里实现最小版本。不是把整个系统抄一遍，是验证核心机制。

例子：

| 观察到的设计 | 最小复现 |
| --- | --- |
| 多 catalog 的 Addressables 分模块热更 | 建两个 group，各自远程 catalog，验证独立更新 |
| 战斗用定点数做帧同步 | 写个 Fixed64，跑两端相同输入，对比 1000 帧后的状态哈希 |
| UI 用一个 Canvas + 自定义深度排序 | 建 50 个 UI 元素，对比多 Canvas 与单 Canvas 的重建开销 |
| 自研 bundle 管理的引用计数卸载 | 实现引用计数，用 Profiler 验证卸载时机 |

复现工程放在 `targets/<game>/repro/`，跑通了在报告里补一句结论（"确实有效" / "在我的场景下反而更慢，因为…"）。

**这一步筛掉了 90% 的伪学习。** 能复现说明理解了机制，不能复现说明只是记住了名词。

## 横向对比

积累到 5 个以上目标后，真正的价值出现：把所有 `urecon.json` 汇总起来做对比。

```bash
urecon compare targets/*/urecon.json
```

会看到这类模式：
- 同品类的游戏在分包粒度上是否收敛到相似的值
- 大厂与小团队在中间件选择上的分歧
- 同一引擎版本区间里，主流方案的迁移趋势（比如从 Lua 热更转 HybridCLR）

单个游戏的方案可能是历史包袱，多个游戏的共同选择才是行业经验。这是这条工具流做成"流水线"而不是"一次性拆包"的根本原因。

## 节奏建议

不要一次做完全套。按目标定深度：

| 深度 | 投入 | 做到哪步 | 适用 |
| --- | --- | --- | --- |
| 侦察级 | 很浅 | Step 1–2 | 只想知道技术栈 |
| 结构级 | 中 | Step 1–5 | 学工程组织与资源管线 |
| 完整级 | 深 | Step 1–8 + 复现 | 有明确要学的具体系统 |

大部分情况下结构级就够了。完整级留给那些"我下个项目就要做这个系统"的目标。
